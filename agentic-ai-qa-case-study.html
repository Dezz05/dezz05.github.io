QA DESIGN CASE STUDY / AGENTIC AI

From AI suggestions to
controlled QA agents.

How I would design an agentic AI workflow that helps a QA team move from requirements to risk-focused test evidence. The goal is not to give an AI agent unrestricted control; it is to define a narrow job, limited tools, observable decisions, and clear human approval points.

Agentic AIRisk-based testingHuman-in-the-loopTest designGovernance & evaluation
Scope note: This is a conceptual design case study and proposed workflow—not a claim that I have deployed an autonomous QA agent in a production environment. The workflow and success measures below are design recommendations to validate with a controlled proof of concept.

01 / THE QA PROBLEM

Useful autonomy needs boundaries.

AI can draft scenarios quickly, but a QA team still has to decide whether those scenarios reflect the requirement, cover meaningful risk, and produce trustworthy evidence. Giving an agent tools to read tickets, write tests, or execute workflows adds value only when its actions can be controlled and reviewed.

THE OPPORTUNITY

Reduce repetitive analysis

Turn approved user stories, acceptance criteria, API specifications, and known defects into a traceable first draft of risks, test scenarios, data needs, and validation steps.

THE FAILURE MODE

Do not confuse plausible output with correct output

An agent may invent requirements, miss a boundary, misuse a tool, or report a result without enough evidence. Those are quality risks—not details to leave for later.

02 / ILLUSTRATIVE WORKFLOW

A bounded agent loop, not an unchecked robot.

Example input: a feature story says a discount code is accepted only when it is active and the basket meets its minimum value. The workflow below is a design proposal for how a QA agent could assist.

01

Read approved context

Retrieve only the selected story, linked acceptance criteria, approved API documentation, and relevant existing tests. Treat retrieved text as data—not as instructions to override agent policy.

02

Extract and trace requirements

Draft a requirement-to-check map and flag ambiguity, missing thresholds, conflicting rules, and undefined error behaviour for a human to resolve.

03

Prioritise risk and propose scenarios

Suggest positive, negative, boundary, equivalence-class, regression, and abuse cases. Link each scenario to a source requirement and explain why it matters.

04

Request approval before changing or running anything

A QA reviewer approves the plan and test data. Only then may the workflow call allowlisted tools against a designated test environment using synthetic data.

05

Execute deterministic checks and collect evidence

Existing test runners decide pass or fail through explicit assertions. The agent can organise logs, map failures to requirements, and suggest a likely area to investigate—but cannot alter the result to make a run pass.

06

Present findings for human disposition

Produce traceability, run links, logs, open questions, and failure summaries. A named person decides whether a defect is valid, whether coverage is sufficient, and whether a release can proceed.

03 / CONTROL DESIGN

Match autonomy to risk.

Permissions should be narrower than the work an agent can describe in natural language. Start with read-only assistance and earn broader permissions only through evaluation.

ActivitySuggested agent permissionRequired control
Summarise a story or specAllowed on approved sourcesSource links and an explicit list of assumptions or unanswered questions.
Draft test casesAllowed as proposalsRequirement traceability, duplication review, and QA approval before adoption.
Run testsAllowlisted test commands onlyIsolated environment, synthetic data, time/resource limits, and logged tool calls.
Edit tests or test dataPropose changes firstHuman review, version control, and no silent changes to expected results.
Change production data or release statusNot permittedKeep release and high-impact operational decisions with authorised people.

04 / FAILURE MODES & SAFEGUARDS

Test the agent like a software component.

HALLUCINATION

Invented requirements

Require source-linked claims, separate assumptions from facts, and route conflicts or missing acceptance criteria to a person instead of filling gaps silently.

PROMPT INJECTION

Untrusted ticket or page content

Keep system policy separate from retrieved content, restrict available tools, validate arguments, and never allow a document to expand agent permissions.

FALSE CONFIDENCE

Weak or misleading test evidence

Use conventional assertions as the source of test outcomes. Store run IDs and logs; do not treat a fluent summary as proof of a passing test.

DATA & ACCESS

Overexposure or destructive actions

Use least-privilege credentials, secret redaction, isolated environments, synthetic data, restricted network access, and approval for actions with side effects.

05 / PROOF OF CONCEPT SCORECARD

Measure usefulness, not autonomy.

These are proposed evaluation measures, not achieved results. Establish a baseline and test on a fixed, reviewed set of stories before comparing an agent-assisted workflow with current QA practice.

MeasureWhat to evaluateWhy it matters
Requirement traceabilityShare of generated scenarios linked to a valid, approved requirement.Helps reveal ungrounded or irrelevant test suggestions.
Reviewer acceptanceUseful scenarios accepted, materially revised, or rejected by experienced QA reviewers.Tests practical quality rather than the raw amount of generated content.

06 / DESIGN TAKEAWAY

Let the agent accelerate the work. Keep QA accountable for the decision.

My position: Agentic AI is most promising when it coordinates narrow, testable tasks—requirement analysis, scenario proposals, execution orchestration, and evidence summarisation—inside explicit boundaries. A credible QA workflow still needs human challenge, reproducible automation, permission controls, and clear release accountability.
